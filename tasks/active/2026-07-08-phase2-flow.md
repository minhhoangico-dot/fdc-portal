## 1. Goal (one sentence)

Collapse the two-page approval workflow (`requests` "của tôi" + `approvals` "chờ tôi", two surfaces over the *same* `fdc_approval_requests` object) into (a) one unified **inbox** "Cần xử lý" at `/inbox` and (b) one **two-lens workspace** (Của tôi / Chờ tôi), and spend the design system's one aesthetic risk — the **con dấu đỏ** `SealMark` — on fully-approved request detail + export only.

## 3. Inbox data model (the load-bearing contract)

The badge (`useActionableCount`) and the inbox list must **never disagree**. Today the badge is:

```
useActionableCount().total
  = useApprovals({enabled}).approvalWorkQueue.totalCount   // = approvals + reviewerIntakes + handoffs
  + useNotifications().unreadCount                          // all unread
```

`approvalWorkQueue` is built by `lib/approvals/workqueue.ts::buildApprovalWorkQueue` from three arrays already derived inside `useApprovals`:
- `pendingApprovals` — requests where `canTakeAction(request)` (pending step assigned to me / my role / my delegation), gated by `approvals.review_assigned`.
- `reviewerQueue` — `fdc_room_intakes` in `submitted|in_review`, gated by `room_management.review_group_queue`.
- `assignedHandoffs` — open `fdc_request_handoffs` (`pending|received`), gated by `approvals.receive_handoff`.

### 3.1 The single-source-of-truth pure function

Add `src/lib/inbox/buildInbox.ts` — a **pure** mapper that emits exactly one `InboxItem` per queue element:

```
InboxCategory = 'phe-duyet' | 'ban-giao' | 'thong-bao'   // chips: Phê duyệt / Bàn giao / Thông báo

InboxItem =
  | { kind:'approval';     category:'phe-duyet'; id; requestId; title; fromName; createdAt; requiresManualForward; amount? }
  | { kind:'review';       category:'phe-duyet'; id; intakeId; title; fromName; createdAt; intakeType:'material'|'maintenance' }
  | { kind:'handoff';      category:'ban-giao';  id; requestId; title; fromName; createdAt; status }
  | { kind:'notification'; category:'thong-bao'; id; title; body; createdAt; linkTo? }

buildInbox({ workQueue, notifications }): InboxItem[]
  = workQueue.approvals.map(→approval)
  ∪ workQueue.reviewerIntakes.map(→review)
  ∪ workQueue.handoffs.map(→handoff)
  ∪ notifications.filter(n => !n.isRead).map(→notification)
```

**Invariant (must be a unit test):** `buildInbox({workQueue, notifications}).length === workQueue.totalCount + notifications.filter(!isRead).length === useActionableCount().total`. Because the map is strictly 1:1 over the same in-memory arrays the badge counts, the list and badge can never drift.

> **Reviewer intakes map to the `Phê duyệt` chip, not a 4th chip.** Direction §4.4 fixes exactly three chips; room review work is "chờ tôi duyệt/xử lý" and folds under Phê duyệt. This keeps the badge arithmetic (which already includes `reviewerIntakes`) equal to the list with zero change to `useActionableCount`. Documented deviation from a literal reading of §4.4's "steps + handoffs + notifications" — required to honor "badge and list never disagree" without editing the count hook.

> **Notification/approval overlap is preserved, not deduped.** An approval frequently also produces an unread "cần duyệt" notification; today the badge double-counts it (workQueue + unread). Deduping the list would make it disagree with the badge; deduping both changes the badge number (needs Minh's sign-off). So Phase 2 keeps them as separate lanes. Future refinement: dedupe by `requestId` in both `buildInbox` and the count — deferred.

### 3.2 The inbox viewmodel

Add `src/viewmodels/useInbox.ts` — composes the existing hooks (no new query patterns, no edits to them):

```
const approvalEnabled = user && (can(review_assigned) || can(receive_handoff) || can(review_group_queue))
  // ← replicate useActionableCount's exact predicate, with a comment tying them together
const approvals = useApprovals({ enabled: approvalEnabled })   // data + action fns from ONE instance
const { notifications, markAsRead } = useNotifications()
const items = useMemo(() => buildInbox({ workQueue: approvals.approvalWorkQueue, notifications }), …)
```

Actions route straight back through `useApprovals`/`useNotifications` (no duplicated approval logic — same requirement `ChoBanDuyet` already satisfies):
- approval → `approvals.approveRequest(id)` / `approvals.rejectRequest(id, note)`
- handoff  → `approvals.updateHandoffStatus(id, 'received'|'completed')`
- notification → `markAsRead(id)` (+ navigate `linkTo`)
- review (material multi-select consolidation / maintenance promote) → **not inline**; row's action is "Mở" → the Chờ tôi lens, where the existing multi-select consolidation UX lives.

**Optimistic removal:** local `dismissedIds: Set<string>`; acting adds the id, filtering it from `items` immediately; the shared-table realtime refetch inside `useApprovals`/`useNotifications` reconciles and the id naturally leaves the source arrays. Reset `dismissedIds` when the underlying arrays change (ids no longer present can be pruned).

## 5. SealMark (§5.3 — the one aesthetic risk, spent once)

`src/ui/SealMark.tsx` — circular **con dấu đỏ**: vermilion `--color-danger-600` ring, slight fixed rotation (~ -6°), approver name + `hoàn tất phê duyệt` + date centred inside. Pure presentational; props `{ approverName, date, roleLabel? }`. **No animation.** Restraint rules baked into placement, not the component.

**Fully-approved predicate** (the ONLY render gate — put in `buildInbox`'s sibling or a small `lib/requests/approvalState.ts` pure helper so it is testable and reused by detail + print):
```
isFullyApproved(request) =
  (request.status === 'approved' || request.status === 'completed')
  && request.approvalSteps.length > 0
  && request.approvalSteps.every(s => s.status !== 'pending' && s.status !== 'rejected')
  // 'forwarded' history steps allowed (escalated-then-approved); final approver = highest-stepOrder 'approved' step with actedAt
```

**Placement (exhaustive — nowhere else):**
1. `src/app/requests/[id]/page.tsx` — when `isFullyApproved`, render `SealMark` in the detail header/summary card (over the status row). Add a `Xuất / In` button that routes to the print view. Everything else on this page unchanged (it still hosts the Chờ tôi action panel via `useApprovals`).
2. `src/app/requests/[id]/print/page.tsx` — NEW print/export view: clean document layout of the request with the `SealMark` bottom-right (the VN paperwork grammar). Screen + `@media print`. Integrator adds the route.

Lists (inbox rows, both lenses, home widgets) use `StatusBadge` only — the circular-seal vs rectangular-badge contrast is what keeps red-as-danger unambiguous elsewhere.

## 6. Realtime consolidation plan

**Current overlap (audit §5):** `useApprovals` (`public:fdc_approvals`, 6 tables) and `useRequests` (`public:fdc_approval_requests`, 3 tables) both subscribe to `fdc_approval_requests/_steps/_attachments` and are frequently mounted together → two channels for the same events. `RequestDetailPage` mounts both; the shell's `useActionableCount` mounts a third `useApprovals`; Home's `ChoBanDuyet` a fourth.

**Phase 2 stance (deliberately incremental, low-risk):**
1. **Do not rewrite the engines this phase.** `useApprovals`/`useRequests` public APIs stay frozen; the inbox and lenses *compose* them. This is the same benign duplicate-subscription pattern Phase 1 already accepted (duplicate `useBridgeHeartbeat`/`useActionableCount`).
2. **Structural removal comes from consolidation, not rewrite.** When the integrator flips `/requests` and `/approvals` to the single `WorkflowWorkspace` and old pages retire, the redundant `useRequests`-only subscription path on `/requests` disappears — the merge "naturally fixes this" as the audit predicted.
3. **Recommended follow-up (integrator, optional, not a wave item):** hoist ONE `useApprovals({enabled}) + useNotifications()` instance into an `ActionableDataContext` at `AppShell` level; have both `useActionableCount` (badge) and `useInbox` (list) read from it. That collapses the shell+inbox duplicate channels into one and makes the count-agreement invariant hold by *shared reference*, not just arithmetic. Left out of the build waves because it edits `AppShell`/frozen hooks (cross-cutting wiring).
4. **No raw `supabase.channel()`** anywhere new — everything still flows through the existing hooks (which use `subscribeToPostgresChanges`).
